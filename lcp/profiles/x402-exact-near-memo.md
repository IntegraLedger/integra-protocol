**LCP profile `x402/exact/near/memo`: the ATR hash as the NEP-141 transfer memo.**

1. The resource server's `PaymentRequired` carries `extensions.legalContext.info` = `{"type":"sha256","value":H,"legalContextUrl":L}`. H is the SHA-256 of the ATR's exact bytes, as `0x` lowercase hex, and L is an `https` URL that serves those bytes.
2. The client fetches L, computes SHA-256 over the bytes received, and compares the result with H as 32 decoded bytes. On a mismatch it does not sign.
3. On a match, the client signs the delegate action x402's NEAR scheme defines, with `ft_transfer` args `{"receiver_id":…,"amount":…,"memo":"lcp:sha256:"+H}` ([LCP §8.1](https://github.com/legal-context-protocol/legal-context-protocol/blob/main/spec/legal-context-protocol-v1.md#81-naming-conventions)), and echoes `extensions` unchanged. `build`'s `near-delegate` request carries, beside `hash`, `delegateAction`: the borsh bytes of the delegate action whose NEP-461-prefixed SHA-256 is `hash`, which `nearRequest` reads back to that hash and to every member the key signs.
4. The server refuses a payment whose `memo` does not decode to an H that it issued for that request and has not seen claimed.
5. H is on chain in the delegated `ft_transfer` arguments, and in the token's `ft_transfer` event where the token follows NEP-141's events. A read finds the payer's act by the payer's access key, the delegate action's sender and public key: the change of that key that carried its nonce to or past the delegate's nonce, read from the block after the position the caller gives (the final block height when the option was issued) up to the delegate's `max_block_height`, and, where the nonce is read at or past the signed one, up to the block it was read so at, since a delegate action the payer signs again over the same nonce carries a later `max_block_height`. The transaction that carried the change is read with the RPC's `EXPERIMENTAL_tx_status`. A transaction hash a settler names is a hint: it shortens the search and proves nothing. Positions are block heights; a search position is the height below which the search read every change, given where it stopped below the latest head. The marks are optimistic, the latest head, and `FINAL`, the final mark, at which alone a read answers `failed`. The key's nonce is read at both: a nonce below the signed one at both is `instrument-live` until rule 8's lapse.
6. x402's NEAR scheme leaves `memo` to the client. A client that does not implement this profile writes none, and rule 4 refuses its payment.
7. **Succeeded** means: the payer's account ran the delegate action, its receipt's outcome a success, and the receipt the token contract executed for the delegate's one action has outcome success, its memo H; the relayer's transaction is `FINAL` at the final mark, or executed at the optimistic one. The token and the `receiver_id` are recorded as read. On a payment the `receiver_id` is compared with the option's `payTo`, and a delegate action paying another account pays nothing; the amount and the token are compared with nothing. A delegate action the payer's account ran whose token receipt failed consumed the key's nonce. One refused for its signature or its expiry consumed nothing, and can still land until `max_block_height`. One refused for its nonce shows the nonce already taken, and the search decides: the act is the delegate action that took it where it is this one under another transaction. A transaction whose token receipt has not yet run is below the mark. What moved names the one transfer by the relayer's transaction and, as its place, the id of the receipt the token contract executed for the delegate's one action. The signer an answer names, for the act and for a foreign item alike, is the delegate action's sender, and its authority the public key the sender signed with.
8. **The lapse.** The delegate action can no longer land where the key's nonce is still below the signed nonce at a final block past `max_block_height`. The read answers it `instrument-unused` only where the search for H, the changes of every access key of the payer's account from the issue position to the latest head at the read, each read through the transaction that carried it, is read whole and finds no delegate action of the payer's that carries H and is the act asked about: a delegate action the payer signs with another of its keys is the payer's act. A nonce at or past the signed one whose change is not found, and a key absent at either read, as one the payer deleted is, whose nonce is then unread, are `search-incomplete`, never a lapse and never `not-found`, whatever the search shows; a nonce past the signed one is never a lapse by itself. Every `failed` but `before-position` waits for that search read whole; until rule 9's run, no search is read whole, so the read answers those `pending`, `search-incomplete`. A change whose transaction the reader cannot name stops the search at the block before it, from which the next read resumes. A transaction the reader cannot read is named as an item the search could not decode, the search held at the block before it and reading on (`read-status`, rule 19); one the caller gave as another act is named `given`.
9. **Shown, and not yet shown, by a run.** A run on `near:testnet` showed, on a payer's account with one access key, that the access-key changes show a relayed delegate action's nonce change from the issue position, and that a reader names the relayer's transaction from that change, whose cause is the delegate action's receipt (transaction `Lbk2JQucgSdTxjtnMrZa4d7roVx8H4vKHyyUeEVviYC`, found by the search with no transaction named). Not yet shown by a run: that the changes of every key of the account show every delegate action of the account. Until a run shows it, a search read whole proves no absence (`read-status`, rule 25). A run showed that NEAR's RPC does not read a transaction by its hash alone: its transaction status method takes the hash with the signer's account, or the signed transaction, and refuses a hash without an account (nearcore 2.14.1 on testnet), so a reader that `recover` is given resolves the signer itself, as a seller's reader can from the accounts that relayed its payments, and a party holding only the hash has no read.
10. **The payment presented** is the NEP-366 delegate action the payer signed, whole, its signature apart: its sender, its receiver, its one function call with its method, arguments, gas and deposit, its nonce, its `max_block_height` and its public key. A `settled` answer states `presented` `yes` where the delegate action it settled on equals that one in every member, and `no` where one differs. The comparison judges no term and decides no answer. `reference` keeps those members, the arguments by their SHA-256, with the option's `payTo` as the payee, and refuses a presented `accepted` that is not the option it is given, compared as RFC 8785 JSON, with `x402/accepted-not-option`.
11. **The agreement.** A payment of this form can itself be the agreement. Its floor is 1 atomic unit of the token: the standard token refuses a zero `ft_transfer` (inferred, not yet shown). The relayer pays the fee, always: it submits the delegate action, pays the gas and prepays the 1 yoctoNEAR deposit; the delegate action names no relayer, so nothing about the fee is fixed in what the payer signs. The transaction must succeed as rule 7 states; one included with a failed result is no agreement. The payee's own signature is no agreement: a delegate action whose sender is the option's payee is never the act, on either act. An agreement is held to no account.
12. Cases of the read kit this read cannot meet, which the form `test/read-kit/forms/near.ts` skips, each with its reason: on `x402/exact/near`, `not-found`, since the read holds the single-use value, the access key's nonce, where the key is present at both reads, and a key absent at either read, as one the payer deleted is, leaves the value unread and is answered `pending`, `search-incomplete`, never `not-found`, whatever the search shows, a search read whole included: the value may have been taken before the key went, and no state in which it may have been taken is answered `not-found`; by the cases' words, *a payment act carrying H that transferred zero* and *an act carrying H that transferred zero*, since the standard token refuses a zero `ft_transfer` (rule 11, inferred); *each transfer of what moved is named by its transaction and its place in it*, since a delegate holds one action, an `ft_transfer`, which moves one transfer (rule 7); *a read that did not read the value at the latest head*, since the read reads the access key's nonce and its changes to the latest head; *an act the read cannot place against the position given* (its three cases) and *an item the search could not decode that gives no position*, since the search reads changes by block; and, while no run has shown the search whole (rule 9), each case whose answer on the act is `instrument-unused`, `instrument-consumed` or `transaction-failed`. Through the read each of those answers `pending`, `search-incomplete`, as the vectors' read rows hold.
