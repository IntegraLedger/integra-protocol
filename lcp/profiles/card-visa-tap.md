**LCP profile `card/visa-tap`: the ATR hash in a Trusted Agent Protocol checkout request.** This profile targets Visa's Trusted Agent Protocol as its specification publishes it (`https://developer.visa.com/docs/trusted-agent-protocol/trusted-agent-protocol-specifications.md`, read 2026-11-16, SHA-256 `7f2408c64c2723c4…`) and its reference implementation, `visa/trusted-agent-protocol` at `16d59bd`.

1. Before payment the merchant shows `{"legalContext":{"type":"sha256","value":H,"legalContextUrl":L}}`, with `legalContextAgreementUrl` after the link where an agreement URL is given. H is the SHA-256 of the ATR's exact bytes (`0x`, lowercase hex) and L an `https` URL serving them.
2. The agent fetches L, hashes what it receives and compares with H as 32 decoded bytes; on a mismatch it does not pay.
3. On a match the agent's checkout request carries H in what its message signature covers, in one of two places, or both:
   - **The nonce.** The `nonce` parameter of its `agent-payer-auth` signature is the base64 (RFC 4648 §4, with padding) of 64 bytes: H's 32 bytes, then 32 bytes the agent draws at random. That is 88 characters, the shape of the specification's example nonce. Every signature in the request carries the same nonce, as the specification's nonce row asks. lcp's `build` gives the nonce.
   - **The checkout path,** for a stock agent, whose nonce does not carry H: Visa's reference agent draws its nonce as a UUID (`tap-agent/agent_app.py:1439`, `:1499`), and an agent may draw 64 random bytes, the shape of the specification's example nonce. The merchant's checkout path ends in a segment that is H, `0x` and 64 lowercase hex digits (for example `/checkout/0x…`), and the agent's signature covers `@path`, which the specification requires of every trusted agent.
4. `bound` takes the request's `Signature-Input` and `Signature` fields and, for the path, the request's absolute path without its query, as RFC 9421 §2.2.6 defines `@path`. It reads every signature whose `tag` is the String `agent-payer-auth`. There must be one, and one of them must have its `Signature` member. Each must carry H: by `@path`, listed with no parameters among its covered components, where the path's last segment is H, its nonce then not read; otherwise by its nonce, where the nonce is the base64 of 64 bytes. Every such signature must carry the same H. No signature, key, window or nonce use is verified here: that is the merchant's recognition of the agent.
5. Where the signature covers no path ending in a hash, any nonce of 64 bytes is read as H followed by random bytes. A request from an agent that draws such a nonce at random, as the specification's own example does, on a path that carries no H, therefore gives a hash the merchant did not issue, and the merchant refuses it at rule 6. On a checkout path that carries H the nonce is not read, so such an agent pays by the path (`card.json` `T2`).
6. The merchant refuses a request whose H it did not issue for this checkout, or whose H it has seen used.
7. The `Signature-Input` field is an RFC 9651 Dictionary. Beside RFC 9421's `keyid`, lcp admits one parameter name in another spelling, `keyId`, as Visa's reference agent writes it and its verifier reads it (`tap-agent/agent_app.py:1331`, `:1364`; `cdn-proxy/server.js:213-254`). No other name with an upper-case letter is admitted, and a signature that names both `keyid` and `keyId` is refused.
8. The card authorization does not carry H. The merchant's processor reference may carry `lcp:sha256:H` as its own record.
9. The requests TAP's specification and its reference implementation publish are this profile's refusal vectors (`card.json`, `T3`). None carries a hash a merchant issued.
10. **What a record proves**, as each pairing's `data.proves` states it; a record fills in the values set in angle brackets:
    - `card/visa-tap`: An account signed an agreement transaction carrying this ATR's hash on `<network>`, recorded in `<transaction>`, before this payment was taken or reported. This shows neither that the account is this payment's payer nor when this payment was taken, which nothing here reads. Every TAP agent-payer-auth message signature in the agent's checkout request covers this ATR's hash: its nonce, whose first 32 bytes are the hash, or the request's path, whose last segment is the hash. The seller checked where the hash rides and did not verify a signature here, which belongs to its TAP recognition step, and nothing compares the agent's key with the account that signed the agreement. The card authorization itself does not carry the hash. This does not show that amount, payee or timing match the ATR's content.
