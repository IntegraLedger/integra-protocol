**LCP profile `ack/payment-request`.** This profile targets ACK protocol version 2025-05-04.

1. The server's Payment Request `id` is `lcp:sha256:H`, signed in its Payment Request token, and the 402 body carries `"legalContext":{"type":"sha256","value":H,"legalContextUrl":L}` beside it. The body names the token `paymentRequestToken`, as ACK's SDKs write it from 0.10.0, or `paymentToken`, as they wrote it before (`agentcommercekit/ack` commit `27e3ffb`, 2025-09-01; at its parent `6fc3247`, `packages/ack-pay/src/create-payment-request-body.ts:28-31`). A reader takes either name; a body that carries both carries one token under both names, and one whose two members differ is refused as a malformed token is.
2. The client reads H from the signed token and compares it with `legalContext.value` as 32 decoded bytes, then fetches L, hashes what it receives and compares again; on any mismatch it does not pay.
3. The client signs nothing that carries H: ACK defines no payer signature.
4. After settlement the receipt's `credentialSubject` carries the token, under either name by the same rule (`create-payment-receipt.ts:30-33` at `6fc3247`; `:30` at `3db94d6`), with H as its `id`.
5. A stock ACK client reads the 402 body as an object of `paymentRequestToken` and `paymentRequest` alone and drops `legalContext` without refusing it (`demos/payments/src/index.ts:165-171` at `3db94d6`), so a buyer whose client is stock never sees L. A client that is to check the ATR before it pays, or to make an agreement first, reads `legalContext` itself.
6. **What a record proves**, as each pairing's `data.proves` states it; a record fills in the values set in angle brackets:
   - `ack/payment-request`: An account signed an agreement transaction carrying this ATR's hash on `<network>`, recorded in `<transaction>`, before this payment was taken or reported. This shows neither that the account is this payment's payer nor when this payment was taken, which nothing here reads. This ATR's hash is the id of the seller's ACK Payment Request token, with the link beside it; a receipt for that request embeds the token. The token's signature is not verified here. ACK defines no payer signature, so nothing the payer signed carries the hash, and the payment, which the payer's side sends before it presents the receipt, is known from the seller's report alone. This does not show that the payer's approval carried the hash.
