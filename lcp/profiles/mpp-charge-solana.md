**LCP profile `mpp/charge/solana`: the ATR hash as the Solana charge's Memo instruction.** Clauses 1–3 and 5 of `mpp/charge` apply to the challenge.

1. The request's `externalId` is `lcp:sha256:0x` + 64 lowercase hex of H, 77 UTF-8 bytes. A request whose `externalId` is present with another value is refused `svm/carrier-occupied`: the scheme has one memo, and a seller's own reference belongs in the ATR's content.
2. MPP says the client SHOULD, not MUST, write the memo; this profile makes it required. The client writes `externalId` as a Memo Program instruction (`MemoSq4gqABAXKb96qnH8TysNcWxMyWCqXgDLGmfcHr` or `Memo4c2pN8afCj432Lb7RMVKi9PbQnnW7ewFFaV3oAH`) of the transaction it signs.
3. Among the transaction's top-level Memo instructions, exactly one has data that parses as an LCP string, and it equals the echoed request's `externalId`. Other Memo instructions, such as split labels, are not read.
4. `type="bundle"`: the carrier is read from the last transaction, which MUST contain the confidential `Transfer`. MPP: *"A server that does include a memo MUST treat the resulting order-id linkage as an explicit privacy trade-off, and MUST verify any memo present in the bundle matches the value it issued."*
5. `type="signature"`: the client has already broadcast, so the server reads the landed transaction and applies clause 3 to it. The money has moved before the check, so a failed check is reported to the seller, never a refusal.
6. What a record of this pairing proves: the payer signed a Solana transaction whose one Memo instruction carries this ATR's hash in LCP string form, and the transaction executed without error, carrying a token or SOL transfer. The memo is in the transaction's instruction data on chain. This does not show that amount, recipient, mint or timing match the ATR's content.
