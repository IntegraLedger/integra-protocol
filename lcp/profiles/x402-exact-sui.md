**LCP profile `x402/exact/sui`: the ATR hash as the one unused Pure input.**

1. The resource server's `PaymentRequired` carries `extensions.legalContext.info` = `{"type":"sha256","value":H,"legalContextUrl":L}`, as in the profile `x402/exact/eip155/eip3009`. The option's `network` is `sui:mainnet`, `sui:testnet` or `sui:devnet`.
2. The client fetches L, computes SHA-256 over the bytes received, and compares it with H as 32 decoded bytes. On a mismatch it does not sign.
3. On a match, the client builds the `exact` payment, adds H's 32 bytes as one `Pure` input that no command uses, signs, and echoes `extensions` unchanged.
4. The server refuses a payment whose transaction does not carry exactly one unused `Pure` input equal to an H it issued for that request and has not seen claimed.
5. H is on chain in the executed transaction's input list; whoever holds the digest can read it back while a node retains the transaction.
6. A client that does not implement this profile adds no unused input, and rule 4 refuses its payment before it is verified or settled.

**The gas paths.** The buyer signs the gas data, so the path is fixed in the option before the buyer signs, and the seller chooses it.

7. Three paths. **Sponsored**: the option carries `extra.gasStation`, an endpoint of the sponsor, as x402's Sui scheme defines it; the client sends the transaction without gas data there, the sponsor fills the gas data (owner, payment, price, budget) and returns the whole transaction, and the client signs it only where it equals the one it sent in everything but the gas data: its `complete` takes the transaction sent and refuses a signed one that differs from it in the sender, the kind (the inputs and commands) or the expiration, and one given with no transaction sent, `sui/not-as-sent`. The sponsor fills and co-signs only a transaction none of whose commands names `GasCoin` and that withdraws nothing from the sponsor, since Sui lets a sponsored transaction's commands spend the gas coin beyond the budget, and co-signs only gas data its own gas station filled; it keeps a gas coin it filled out of other use until the payment can no longer land. **Gasless**: the option carries `extra.gasless: true`, which the scheme does not define; the gas data holds an empty payment, price 0 and budget 0, and Sui admits the transaction only where it moves a coin type on the network's gasless list, at least that coin type's smallest transfer, with at most one unused `Pure` input and no `Pure` input over 32 bytes, which H's 32 raw bytes meet, and with `MoveCall`, `MergeCoins` and `SplitCoins` commands alone, so the transfer is `0x2::coin::send_funds` to the payee's address balance and never `TransferObjects`. **The buyer pays**: neither member; the buyer owns the gas data. An option carrying both members, or either in another form, is not this pairing's.
8. A settler checks, by x402's Sui scheme, the network, the signature, a simulation that succeeds for a transaction not executed, and the payee's balance change. A passing simulation does not show that the transaction can execute: Sui's simulation takes each owned input at its latest version, and answers success for a transaction whose gas coin the buyer has since spent, which execution refuses. So a settler also checks that each object the transaction names at a version (its gas payment, each owned or immutable input, each object it receives) is not shown by the node at a later version, as no longer live, or with another digest at that version. With this profile it also checks the one unused `Pure` input equal to an H the resource server issued, on the sponsored path rule 7's checks, and at `"0"` that the signed transfer names the option's payee. A transaction the buyer already executed, which it can do on the buyer-pays and gasless paths, is judged by its effects (status success, the unused input, the payee's credit) in place of the simulation, and is not refused for having executed.

**The read.** `status` reads through a GraphQL endpoint the caller supplies, and states what the transaction shows; it compares no amount, coin type or time with the option.

9. **What moved, and the account a payment names.** What moved is the effects' balance changes, each one owner's net change in one coin type, a coin type being any struct type, with type parameters where it has them, of at most 4096 characters: each positive change is recorded with its coin type, its amount and its owner, the account it reached, named by the digest and its place, `<owner>:<coin type>`. A transfer a signed command names whose recipient no positive change in its coin type shows, a transfer of zero or a SUI transfer the recipient's own gas outweighs where the recipient owns the gas data, is recorded with its recipient, the recipient's net change in that coin type where it has one and zero otherwise, named by the digest and its place, the index of the command: a `TransferObjects` whose address is a `Pure` input of 32 bytes, or a call of `0x2::coin::send_funds<T>(coin, recipient)` whose recipient is one; its coin type is `T`, or SUI where every object transferred is split from the gas coin, and where the bytes show none it is recorded with no coin type. A transfer to the sender, such as the remainder a balance intent sends back, is the sender's own and is not recorded. A payment names the payee's account where one of these entries reaches the option's payee, in any coin, zero included; an agreement is held to no account.
10. **The transaction the digest names.** The digest is Blake2b-256 over `TransactionData::` and the signed bytes, the single-use value: it is fixed before any money moves and executes once. The transaction the endpoint returns for it must hash to it, decode, and carry the H asked about as its one unused `Pure` input; otherwise the answer is `unreadable`, `unparseable`, and it releases nothing. Its signer is the sender. It succeeded where its effects' status is success; with status failure it was included with a failed result, gas charged, and it consumed the digest: it is no agreement, it moved nothing, and the account it names is the recipient a signed transfer names (rule 9), the one `read-status.md` rule 20 compares with the option's payee.
11. **Marks.** One mark a query can ask for, `final`: certified effects in a checkpoint, every checkpoint being final. A transaction the endpoint returns with no checkpoint, executed and not yet in one, is in the state `executed`, below that mark, after every checkpoint and so after the position given: `pending`, `below-mark`, naming it, never `settled`. The position is the checkpoint's sequence number.
12. **The lapse.** The transaction can no longer land once the epoch is past the last epoch its expiration names (`Epoch`, or the `maxEpoch` of `ValidDuring` or `Validity`); one with no epoch has no readable bound and is never `failed`. The epoch is read at the search's head (rule 13), or at the endpoint's latest checkpoint where it states no range for the sender filter. An absent digest while the endpoint holds transactions from the position given and the epoch is not past the bound can still land: `pending`, `instrument-live`, and sending the same bytes again gives the same digest.
13. **The search for H.** The digest is over the whole signed data, not over H alone, so its read is no search for H: every `failed` but `before-position` (a lapse, a transaction found by the digest that is not the act asked about, one included with a failed result) waits for the search. It reads the sender's transactions, the sender the reference names, through `transactions` filtered by `sentAddress`, `afterCheckpoint` (the position given, or the search position an earlier answer returned) and `beforeCheckpoint` (one past the search's head), page by page forward until `hasNextPage` is false, at most 8 pages a call. Its head is the last checkpoint of the range the endpoint states it holds for that filter, `serviceConfig.availableRange(type: "Query", field: "transactions", filters: ["sentAddress"])`. Each transaction is read as rule 10 reads the digest's, and is an act of this pairing where its one unused `Pure` input is H: one that succeeded and meets read-status rules 7 to 9 is the act asked about, answered `settled` on it whatever it moved; one signed by the option's payee, one that names no account of the payee's on a payment, and one the caller gave are foreign items; one with a failed result settles nothing; none stops the search. A transaction the endpoint names by its digest and checkpoint that does not hash to that digest, does not decode, or whose other members are out of the reader's form, is named among the items the search could not decode, holds the search's position at the checkpoint before it, and fails nothing else of its page (read-status rule 19); a page whose items cannot be named by a digest and a checkpoint in the range, in checkpoint order, is `unreadable`, `unparseable`. The search's position is the last checkpoint all of whose transactions of the sender were read; the next call takes it.
14. **History.** An absence counts only where the endpoint states that it holds transactions from a checkpoint at or before the position given (`availableRange(type: "Query", field: "transaction")`); otherwise the answer is `unreadable`, `history-gap`. The search is complete only where the range it states for the sender filter begins at or before the position it reads from; a range that is not stated, or begins later, is `unreadable`, `history-gap`.
15. **Not yet shown.** That a GraphQL endpoint serves `sentAddress` with both checkpoint bounds, states the range it holds for that filter, returns the sender's transactions in checkpoint order with their bytes, and answers the range and every page of one search from one view, has not been shown by a run. Until a run shows it, a search read whole proves no absence (read-status rule 25): where the read would answer `failed` for any reason but `before-position`, it answers `pending`, `search-incomplete`, the search's position at its head.

**The agreement.** A payment of this pairing can itself be an agreement.

16. The floor is a rule by gas path: zero where the buyer or a sponsor pays gas, until a run shows it; on the gasless path the coin type's smallest transfer on the network, a parameter of the ledger: the minimum Sui's protocol configuration lists for the coin type among the tokens a gasless transaction may move (`gasless_allowed_token_types`), which the resource server reads for the option's network when it issues the offer. On the gasless path the floor is the larger of that parameter and 1, so it is never an amount the option filter refuses. `suiFloor` evaluates the rule from the gas path and that parameter, and refuses a gas path or a parameter it cannot read (`sui/floor-input`). The option filter admits an amount of `"0"` where a sponsor or the buyer pays gas, and not on the gasless path. Who pays the fee is rule 7's path. The transaction must succeed (rule 10). A transaction whose sender is the option's payee is no agreement, on either act: the read names it a foreign item and never answers `settled` on it.

**The reference.**

17. `reference` gives the network, the digest, the last epoch the expiration names or none, the sender, and the option's payee, the `payTo` of the option it is given, which is the key of the two party tests and no search key. It refuses a payment whose `accepted` is not that option, compared by RFC 8785 form (`x402/accepted-not-option`). A `settled` answer states `presented`: `yes` where its transaction has the reference's digest, which is over the whole transaction data the buyer signed, its signatures apart, and `no` where it is another the search found.

**The read kit.**

18. Declared inapplicable to the read kit: `not-found`, since the read reads the digest, which is the single-use value itself; a value read consumed whose transaction is not found, since the value is the transaction (its cases: *a value read consumed whose transaction the search has not found*, *a value unconsumed at the final mark and consumed at the latest head* and *a value whose validity passed, unconsumed at the final mark and consumed at the latest head*); *an act read at the finality asked for, below the final mark*, since a seller names the one mark; *an act found above the final head*, *a transaction that consumed the value, read below the final mark* and *below-mark is answered before instrument-live*, which give a transaction below the final mark a position, where such a transaction is in no checkpoint, the vectors holding the read's `below-mark` for one (rule 11); *the validity passed with the value unconsumed, read below the final mark*, since the epoch is read at a final checkpoint (rule 12); *an act of another pairing or kind carrying H*, since every transaction whose one unused `Pure` input is H is an act of this one pairing, an agreement and a charge alike (rule 13); *each transfer of what moved is named by its transaction and its place in it*, since the effects carry one net balance change per owner and coin type, so two transfers of one asset to one account in one transaction are one entry of what moved (rule 9); *an act the read cannot place against the position given* (its three cases) and *an item the search could not decode that gives no position*, since every transaction the read meets is in a checkpoint or after all of them; *a read with no means to read the single-use value* and *a read that did not read the value at the latest head*, since the read reads the digest at the latest checkpoint; *the settled act's answer names every foreign item*, *instrument-live is answered before search-incomplete* and *instrument-live is answered before an item the search could not decode*, since the search is made only before a `failed` (rule 13); and, while the search proves no absence (rule 15), each case at coverage `full` whose answer on an act is `instrument-unused`, `instrument-consumed` or `transaction-failed`, which the search's gate holds: the vectors hold the read's answer to such a case, `pending`, `search-incomplete`. A case is named by its reason, or by the opening words of its text in `read-status.json`.
19. **What a record proves**, as each pairing's `data.proves` states it:
    - `x402/exact/sui`: The payer, the sender, signed a Sui transaction whose one unused Pure input is this ATR's hash, and the network executed it successfully in a checkpoint after the position the read was given; the hash is on chain in its input list, readable by its digest while a node retains it. The sender is not the option's payee. Where the transaction moved value it paid each account a positive balance change names; where it moved nothing it was signed, naming the recipient its signed transfer names. What it moved is recorded as observed: this does not show that amount, coin type or timing match the ATR's content.
