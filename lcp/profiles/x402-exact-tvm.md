**LCP profile `x402/exact/tvm`: the ATR hash as the comment in the forward payload of the Jetton transfer a payer's W5 wallet signs.**

*Scope.* x402 v2, `scheme` `"exact"`, `network` `tvm:-239` (mainnet) or `tvm:-3` (testnet), as x402's TON scheme defines it (`specs/schemes/exact/scheme_exact_ton.md` at `x402-foundation/x402@88b66dd4`, "the scheme" below). The option names no `extra.assetTransferMethod`, its `extra.paymentFlow` is absent or `"authorization"`, and its `extra.areFeesSponsored` is `true`. The stock client and settler are `@x402/tvm` 2.30.0, cited by its source files.

1. **Where H rides.** The resource server's `PaymentRequired` carries `extensions.legalContext.info` = `{"type":"sha256","value":H,"legalContextUrl":L}`, H the SHA-256 of the ATR's exact bytes as `0x` lowercase hex and L an `https` URL that serves them; and the option's `extra.forwardPayload` is the base64 bag of cells of one cell with no references: 32 zero bits, TEP-74's text comment tag, then the 77 UTF-8 bytes `lcp:sha256:` followed by H. A stock client copies `extra.forwardPayload` into the Jetton transfer as a reference (the scheme, lines 71 and 174; `src/codecs/jetton.ts:43-44`), so H is in the bytes the payer signs, whole. A stock server always fills `extra.forwardPayload`, by default with the cell of one zero bit, `te6cckEBAQEAAwAAAUD20kA0` (`src/utils.ts:60-62`; `src/exact/server/scheme.ts:98-99`, `:116`). `advertise` reads that cell, in any bag of cells that decodes to it, as an empty carrier and places H's comment there; an option whose `extra.forwardPayload` holds any other cell but H's own comment is refused `tvm/carrier-occupied`. `unplaced` drops `extra.forwardPayload` whatever it holds, so the option as the stock server offered it and as placed unplace alike.
2. **What the payer signs.** One W5 (v5r1) `internal_signed` request: op `0x73696e74`, the wallet id, `valid_until`, the sequence number, the action list as `Maybe ^Cell` holding exactly one `action_send_msg` behind an empty list, and `has_other_actions` 0, signed by the wallet's Ed25519 key over the request cell's representation hash; the signature is the body's last 512 bits. The one message is internal and bounceable, to the payer's Jetton wallet of `asset`, and its body is a TEP-74 `transfer`: a query id, `amount`, the destination `payTo`, the response destination `extra.responseDestination` or `addr_none`, no custom payload, the forward TON amount `extra.forwardTonAmount` or 0, and the forward payload as a reference to H's comment. `valid_until` is the client's clock plus `maxTimeoutSeconds`. The message carries a value above the forward TON amount and at most 30,000,000 nanotons above it, the stock settler's cap (`src/exact/facilitator/scheme.ts:326-329`; `DEFAULT_JETTON_WALLET_MESSAGE_AMOUNT`, `src/constants.ts:14`): `build` refuses an `attachNanotons` at or below the forward amount `tvm/value-too-low`, and above the cap `tvm/value-too-high`. The payment's payload is `{settlementBoc, asset}`: an internal message to the payer's W5 wallet, value 0, with the wallet's state init where the wallet is not deployed, whose body is the signed request.
3. **What the resource server refuses**, before anything moves: an option whose forward payload is occupied (rule 1); a payment whose Jetton transfer carries no forward payload holding a comment with an ATR hash (`tvm/payload-not-lcp`), or one other than the option's (`tvm/carrier-mismatch`); a body W5 does not run as one `internal_signed` request (`tvm/not-w5-signed`); an action list that is not exactly one `action_send_msg` behind an empty list with `has_other_actions` 0, whose one action's send mode is other than 1 or 3, the two the scheme admits (line 170), or whose message is not bounceable, `tvm/actions`, the error under which the stock settler's codec refuses each (`src/exact/codec.ts:61`, `:66-72`); and a bag of cells over 8 KiB, 512 cells or depth 32 (`tvm/boc-too-large`). A request with any other mode is refused because TON's other modes include those that remove the sending account once its balance reaches zero, and with it the sequence number rule 6's read rests on.
4. **What a settler checks**, by the scheme (lines 150-180): the signature against the wallet's key, the wallet's code on the scheme's list, which holds W5R1's `20834b7b72b112147e1b2fb457b84e74d1a30f04f737d4f62a668e9552d2b72f` (line 166), the amount, destination, response destination, forward TON amount and forward payload against the requirements' effective values, the attached value against the cap of rule 2, `valid_until`, and the sequence number. The settler relays the signed request to the payer's W5 wallet from its own wallet and pays the gas, always: the scheme defines only that flow (lines 16 and 24).
5. **The reference** `reference(presented, option)` gives: the network; the option's payee, its `payTo` as a raw address, for both party tests of rule 6 and no search key; H; the representation hash of the request body, its signature included, by which the read finds the request; `signedHash`, the representation hash of the request with its signature removed, the hash the wallet key signs, which holds the members of the payment presented: the W5 request the payer signed, whole, its signature apart; the representation hash of the Jetton transfer's body; the payer's W5 wallet and its Jetton wallet, raw; `validUntil`; `seqno`, the sequence number the request was signed against, the single-use value; and `codeHash`, the representation hash of the code in the state init, where the payment carries one. It names no asset. It refuses a presented payment whose `accepted`, its forward payload apart, is not `option`, its forward payload apart, as RFC 8785 compares them, `x402/accepted-not-option`: the payment answers another option.
6. **The read.** `status` (profile `read-status`) reads a TON Center v3 index through a reader the caller supplies. A position is a masterchain block's sequence number, and a transaction is at a position by its `mc_block_seqno`. The marks are `confirmed` and `finalized`, TON Center's finality states 1 and 2; the final mark is `finalized`. A run of a request is a transaction of the W5 wallet that did not abort, whose inbound body is a request W5 runs as signed, `internal_signed` or `external_signed`, and whose data hash changed. The act is found by the request's body hash among the W5 wallet's transactions, then the Jetton `transfer` message its run sent, the payer's Jetton wallet's transaction that took it, and that wallet's `internal_transfer` to the Jetton wallet that took it.
   - **Succeeded** means three transactions, none aborted: the W5 wallet's run sent the Jetton `transfer`, the payer's Jetton wallet sent `internal_transfer`, and the Jetton wallet it reached took it. A run that sent no Jetton `transfer`, a Jetton wallet that sent no `internal_transfer`, and a delivery that aborted are failed results that consumed the sequence number. A failed result moved nothing, so the account it names is the destination of the Jetton `transfer` the payer signed; it is the act's own failed result, `transaction-failed`, only where it carries H and, on the act `payment`, that destination is the option's payee, and any other is the transaction of an `instrument-consumed` answer (profile `read-status`, rule 20). An aborted W5 transaction, and one the wallet refused for its signature, which returns without aborting, sends nothing and leaves the data hash unchanged, consume nothing and are read as a request not seen.
   - **The two party tests.** On either act the W5 wallet, the signer, is not the option's payee; where it is, the run is a foreign item, `payee-signed`. On the act `payment` the delivering account is the payee's Jetton wallet of the payer's Jetton wallet's master, the master's `get_wallet_address` for `payTo`, read through the index's `runGetMethod`, the master read by `get_wallet_data` on the payer's Jetton wallet; where it is another, the run names another account, `other-account`. An agreement is held to no account. Neither the Jetton nor the amount is compared with anything.
   - **What moved** is each Jetton `transfer` carrying H the run sent, one for a request of this form: the payer's Jetton wallet's master as the asset, the `internal_transfer` amount, zero included, and the delivering account, named by the W5 transaction and, among its out messages, as its `place`, the Jetton `transfer` message's hash. The signer is the W5 wallet. On `settled`, where the reference holds `signedHash`, `presented` is `yes` where the act is the request found by its body hash, or where the run's request, its signature apart, has the reference's `signedHash`, `no` where it has another, and `unshown` where the read cannot hash it: the read hashes the ordinary cells it decodes, and a request holding an exotic cell is `unshown`.
   - **The expiry read, which is the search for H.** The read takes the index's statement of the masterchain blocks it holds, from its first block through a finalized block, with that block's time; the wallet's state as the index holds it, its status, code hash, sequence number and last transaction; and the wallet's transactions from that last one back, each by its predecessor, to the first at or before the position the caller gave, or to the wallet's first, at most 256. Each listed transaction gives its inbound body, whether it aborted, its out messages with their bodies, its masterchain block, its predecessor, and the account's status and data hash before and after it. A wallet is W5 where its code hash, from its state, or from the reference's `codeHash` while it is `uninit` or `nonexist`, is W5R1's. Every listed run whose Jetton `transfer` carries H, at the signed number or another, is followed as the request is, and tested by the two party tests; a listed run whose out message is a plain comment holding H is an act of another kind, `other-kind`. W5 also runs the actions an installed extension sends it, op `extn` (`0x6578746e`), from the extension's own account, with no signature of its key and no sequence number (`wallet_v5.fc`, `recv_internal`, at `ton-blockchain/wallet-contract-v5@ff2a9cdb`): a listed transaction of that op whose Jetton `transfer` carries H is followed as a run is, and is a foreign item signed by the extension's account, `payee-signed` where that account is the option's payee and `other-signer` otherwise; it consumes no sequence number. The single-use value is read consumed where a listed run is at the signed number, where the wallet is `active` with a number above the signed one, or where a listed transaction removed the account or deployed it, whose number then starts anew; it is read at the latest head from the wallet's state, and an active wallet whose state the index gives without its number is not read there, which never answers `instrument-live`; it is read consumed at the final mark only where that run lies at or below the stated finalized block, or where the wallet's last transaction does; it has lapsed where the latest head is more than 60 seconds past `validUntil`, a W5 transaction running at its shard block's time, which a masterchain block references only later, and it is read at the final mark only where the stated finalized block is also past that time. A listed transaction whose inbound body, request or Jetton `transfer` the read cannot decode is an item the search could not decode: it is named, in the order of the masterchain blocks, and holds the search there, and it is never `unreadable`. Of two acts that meet every test, the earlier is answered. A frozen account, its code removed, runs no request until a message restores the state its hash fixes, its number among it, so it reads as `uninit` and `nonexist` do: its number not passed, W5 where the code hash its state or the reference gives is W5R1's. A listed run is matched to an other act the caller gave by its reference by the reference's `signedHash`, or by its `requestBodyHash`, the run's inbound body hash; a listed transaction whose account is not a raw address is out of the reader's form. A wallet that is not W5 gets no expiry read: the read has no means to read its value, the lookup by the request's body hash is its search, read whole where the stated block's time is at or past the latest head, and its history is shown where the stated first block is at or before the position the caller gave, or, where the caller gave none, is the masterchain's first.
   - **Not yet shown.** No call by which a TON Center v3 index states the blocks it holds is named in its API definition, and that its wallet state holds every transaction of the blocks it states, and that its listed transactions link whole, have not been shown by a run. The search is therefore never read whole, through any reader, and no answer but `before-position` is `failed` until a run shows both (profile `read-status`, rule 25); no caller's statement stands in for that run. A list read to its end gives no search position.
   - **The search position** names two transactions of the wallet's list, each by its hash and logical time: `top`, the newest the search had listed, and `next`, the one it reads next. The list is a linked list read back from its newest transaction, so a call given a search position lists the transactions above `top`, which landed since, then reads on from `next`, the ones between having been read, and a wallet with more transactions than one call lists is read whole over several. The answer holds the search at the first transaction it must read again: where a run's message is not yet taken, or a transaction lacks a member the read takes, that transaction; where a link does not hold or the list's bound is reached, the transaction it reads next; and where such a transaction is above the given `top`, at the position given. The request found by its body hash alone holds no place in the list.
7. **What a record proves** (rule 5 of the codec contract). At coverage `full`: the payer's W5 wallet signed a request whose one Jetton transfer carries H in its forward payload, and ran it; it paid, through its Jetton wallet, the amount the `internal_transfer` names, zero included, to the Jetton wallet that took it, the recipient; where the read observed no transfer, the W5 wallet signed. The signer is the W5 wallet, named apart from the recipient. Nothing in the record shows that the amount, the Jetton, the payee or the time match the ATR's content.
8. **The agreement.** The payment can itself be the agreement: coverage `full`, single use, one payer-signed act paying a fixed amount with no hold. Its floor is zero: the scheme asks equality with no floor, and the stock settler and the standard Jetton wallet take a zero (lines 155 and 171); so the option filter admits an `amount` of `"0"`, which `build` writes as a Jetton `transfer` of zero. The settler pays the fee, always. The agreement is the request's run that meets "succeeded" (rule 6); a failed one is no agreement. A request the payee's own W5 wallet signed is no agreement and settles no payment, on either act.
9. **The read kit** (profile `read-status`, rule 28). Declared inapplicable to the read kit: while the expiry read releases nothing (rule 6, *Not yet shown*), the cases its gate holds, each case at coverage `full` whose answer on the act is `instrument-unused`, `instrument-consumed` or `transaction-failed`, its search resting on the fact not yet shown; this pairing's vectors and its read give such a case `pending`, `search-incomplete`. The cases of a transaction that carries H under another account's signature, `other-signer`, arise: a W5 wallet runs the actions an extension it has installed sends it, with no key and no sequence number (rule 6). The read-kit form makes one case in this ledger's own spelling, where the rule that decides it treats the two alike: a transaction another account signed that consumed the value is the payer's own run at the signed number, since only a run of a request the wallet's key signed consumes it (rule 16 of `read-status` decides `before-position` before it asks who signed).
10. **Recovery.** `recover({network, tx, option}, reader)` reads the transaction `tx` names, the payer's Jetton wallet's transaction that took the Jetton `transfer`, and returns the H of the comment in its inbound `transfer`'s forward payload. It needs no member of `option`, which must be an object.
