**LCP profile `mpp/charge/usdc/solana`: the ATR hash as the Memo instruction of a `usdc` charge on Solana.** MPP's `charge` intent under the `usdc` method, which no stock client implements; lcp's client builds it. Clauses 1–3 and 5 of `mpp/charge` apply to the challenge.

1. The request's `externalId` is `lcp:sha256:0x` + 64 lowercase hex of H, 77 UTF-8 bytes; a request whose `externalId` is present with another value is refused `svm/carrier-occupied`. lcp's client writes it as one Memo Program instruction of the transaction the buyer signs.
2. Among the transaction's top-level Memo instructions exactly one holds an LCP string, spelled as clause 1 gives, equal to the echoed request's `externalId` and naming the H of the challenge's id, as `mpp/charge/solana` clause 3 states. The credential is `type="transaction"` alone; the settler broadcasts.
3. The client builds the highest message version both `methodDetails.transactionVersions` and lcp admit: version 1 where the list holds 1, version 0 where it holds 0 alone or is absent, as `@solana/mpp` builds it where a challenge lists it, in a release later than 0.7.0 (`pay-kit` `86400da`, `typescript/packages/mpp/src/client/Charge.ts:211-220`); a list that admits neither is refused at the filter (`svm/input-malformed`). `bound` and `reference` decode legacy, version 0 and version 1 messages, and refuse one whose version the challenge does not admit, `svm/version-not-admitted`: a payment the option does not admit is no answer to it. The server accepts exactly the versions the challenge lists, the list absent being `[0]`, and refuses a `legacy` message whatever the list holds, before it co-signs (`pay-kit` `86400da`, `typescript/packages/mpp/src/utils/transaction-versions.ts:15-16`, `:218-226`; `src/server/Charge.ts:424-433`, `:1077-1081`), so lcp refuses `legacy` on every challenge, before anything moves.
4. The agreement: its floor is 1 base unit, since the request's `amount` is a positive integer; the fee is paid by the settler where the challenge names it fee payer, else by the buyer; it succeeds as `mpp/charge/solana` clause 8 states.
5. The read, `status`, as the profile `read-status` answers it: one mark, `finalized`, the default and the final mark. The search for H lists the memo-carrying signatures of the buyer's own account, which every transaction the buyer signs loads, never the fee payer's, from the issue slot to the latest head, `confirmed`, which is no mark: 10 pages of 1,000 and 50 candidates a pass, a pass that meets either bound, or a candidate no lookup finds or one that does not decode, holding a handle the next read resumes from, below the pages it read, with the transactions met that the answer rests on, a consumer of the value or one the payer signed, other than those the caller gave, which the next read looks up by signature. An act met only above the `finalized` slot is `pending`, `below-mark`, named with no finality. The parties come from the landed transaction: who signed it, and the owner, as the transaction's token balances name it (`meta.postTokenBalances`), of the token account a transfer from the buyer's token account reaches, top-level or inner; a payment counts where one such transfer reaches the option's payee, zero included, and an agreement is held to no account; each transfer of what moved is named by the transaction and its instruction's place, the top-level index or `<index>.<place>` for an inner instruction, and a transaction with a failed result names the destination the payer signed and moved nothing. `presented` compares the landed message with the one presented, by its digest, or with the transaction presented alone. The single-use value is the signed message: consumed by its own landing or by its durable nonce advanced; unused once its blockhash has lapsed, `isBlockhashValid` answering `false` at `finalized` at a `finalized` slot at least 150 past the context slot of the first `isBlockhashValid` answer of `true` at `confirmed`, which the search's handle keeps, a slot count alone deciding nothing, since a skipped slot adds no block and the chain ends the blockhash's validity 150 blocks after its own, and a blockhash read invalid before such an answer deciding nothing; a durable-nonce message never lapses. Until a run shows every transaction the buyer signs listed under its account, a search read whole proves no absence: no `failed` but `before-position` is answered, `pending`, `search-incomplete` in its place.
6. Declared inapplicable to the read kit, cases the read cannot meet on Solana: the case settled at a finality asked for below the final mark, since a seller names `finalized` alone; while the search proves no absence, every case at coverage `full` whose answer is `instrument-unused`, `instrument-consumed` or `transaction-failed`, which the read answers `pending`, `search-incomplete` (`vectors/svm-read.json`); and, the read holding the signed message, a read that did not read the value at the latest head, since its search and its lookups read on to `confirmed`, and a value whose validity passed, unconsumed at the final mark and consumed at the latest head, since a blockhash message is consumed only by its own transaction, which that read finds, and a durable-nonce message has no lapse.
7. What a record of this pairing proves: the payer's own signed act carries this ATR's hash: a Solana transaction the buyer's account signed, whose one LCP-form Memo instruction is the hash's LCP string, final at `finalized` with no error. It paid each transfer it made from the buyer's account, recorded with its mint or lamports, amount and recipient, one of zero included, the recipient being the owner the transaction's token balances name; as a payment, one of them reached an account the option's payee owns. The memo is in the transaction's instruction data on chain. It compares no amount, mint or time with the ATR's terms.
