**LCP profile `legal-context-return`: the return after an agreement.**

A sale whose charge is paid only after its agreement is recorded (an agreement first) has its buyer make the agreement, then return to the resource server for the charge. This profile fixes what the first response carries, how the buyer's agent returns, and how each agreement option names the charges it serves.

1. **The first response** of such a sale carries H, the ATR's link and the agreement's URL, in the members the sale's protocol places them in: on x402, `extensions.legalContext.info` (`value`, `legalContextUrl`, `legalContextAgreementUrl`); on MPP, each challenge's `opaque` (`legalContext`, `legalContextUrl`, `legalContextAgreementUrl`). It carries no charge option the payer could pay before the agreement.
2. **The `Legal-Context` request header.** A buyer's agent that has made the agreement repeats its request with the header `Legal-Context`, whose value is an RFC 9651 Item: the bare item is a token, H's LCP string `lcp:sha256:0x` followed by H's 64 lowercase hex digits; the one parameter the header may carry is `rv`, the sale's return value (rule 5) as a byte sequence. No other parameter is admitted. The value is parsed as RFC 9651 parses an Item (section 4.2): spaces before and after the item and after each `;`, and none elsewhere; every parameter's value parsed as a bare item (sections 4.2.4 to 4.2.10); a parameter given more than once counting as the last given (section 4.2.3.2); and `rv`'s base64 read with its `=` padding absent and with bits set past its last byte, which section 4.2.7 says a parser should not refuse, and with no character outside the standard base64 alphabet. A value that does not parse, whose token is not H's LCP string in lowercase hex, that carries another parameter, or whose `rv` is not a byte sequence of 32 bytes is refused `return/header-malformed`; so is an H or a return value of another length given to the writer, which writes `rv` padded. Examples: `Legal-Context: lcp:sha256:0xba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`, and with a return value, `…15ad;rv=:<base64 of 32 bytes>:`. A checkout protocol's own session id serves in place of the header where the protocol has one.
3. **The check.** A resource server serves a request as a return only where the header's H is the H its own record holds for the request, and, where the sale has a return value, the header's `rv` is that value. lcp exports the check, pure, as `checkLegalContextReturn(value, record)`: the value parsed as rule 2 parses it (`return/header-malformed`: a header that does not parse is no return); its H held to the record's H (`return/not-this-sale`); and its return value held to the record's, compared in constant time, since it is a bearer secret, an `rv` given for a sale that has none and none given for a sale that has one refused alike (`return/value-mismatch`). A return to a sale whose charge is a Lightning invoice that is refused gets no invoice.
4. **Over MCP**, where a tool call's result has no response header, the first response's tool result carries the header's value (H, with `rv` where the sale has one) in its `_meta` under the key `com.integraledger.lcp/legal-context` (`LEGAL_CONTEXT_META`), and the buyer's agent returns it under the same key in the `params._meta` of each later tool call of the sale. No request commitment covers `params._meta` (`x402/request-commitment`, rule 5). The value's syntax and its check are the header's (rules 2 and 3).
5. **The return value.** Where the sale's charge is paid by a bearer value, such as a Lightning preimage, which every node on the payment's route learns, the first response also carries a return value: 32 bytes drawn at random for the sale by the resource server and kept in its own record, in no ATR and on no ledger. On HTTP the first response carries it in a `Legal-Context` response header of rule 2's syntax, with H. The buyer's agent sends it with H only to that resource server, on the return and on every later request of the sale, and the resource server answers none that lacks it. The form that needs it is the Lightning profiles'.
6. **The charges an agreement option serves.** Each agreement option offered names the sale's charge options whose `agreementOn` admits it, so that a buyer pays an agreement that serves the charge it means to pay. Each charge option is named `<slot>/<i>`: the option at index `i` of the charge options the ATR's binding slot of that name holds, for every binding slot that holds them: `x402/<i>` for `accepts` of the `x402` slot, `mpp/<i>` for `challenges` of the `mpp` slot, `ack/<i>` for `paymentOptions` of the `ack` slot, and `acp/<i>`, `ap2/<i>`, `card/<i>` and `ucp/<i>` for `options` of the slot of that name, so that a buyer that holds the ATR finds each one, a charge option withheld from the first response among them. A card or checkout sale whose agreement is offered as an x402 option or an MPP challenge names its card or checkout options so. A name resolves against the ATR: its slot is the ATR's binding slot, the member after `atrVersion` and `id`, and its index is below the number of charge options that slot holds. On an x402 option the member is `extra.legalContextServes`, an array of 1 to 32 distinct such names; on an MPP challenge it is the `opaque` member `legalContextServes`, those names joined by one space. The member is part of the option as issued, so the digest a resource server records for the option covers it. An option that is not an object, an x402 `extra` that is not an object, an MPP `opaque` that is not base64url of a map of strings, or a member that is not 1 to 32 distinct such names (an index from 0 to 31 with no leading zero, the MPP names joined by exactly one space) is refused `return/serves-malformed`; so is a name that does not resolve against the ATR's bytes where a reader is given them. lcp exports the read as `servesOf(option, atr?)`.
7. The vectors are `legal-context-return.json`: the header written and read, each refusal with one member of a good header changed, the serves member read and refused, alone and against a card ATR whose `card` slot holds three options, and the check: one return that passes and one for each of its refusals, the last a Lightning sale's return without its return value. Their oracle is RFC 9651's parsing algorithm, with each byte sequence decoded by Python's `base64`, and the bare items before an overwritten `rv` are RFC 9651 section 3.3's own examples.
