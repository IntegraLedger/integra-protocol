**LCP profile `card/visa-vic`: the ATR hash as a Visa Intelligent Commerce transaction reference.** This profile targets the credential request of Visa Intelligent Commerce as Visa's reference agent makes it (`visa/vic-reference-agent` at `39bc93d`, cited from `reference-agent-backend/`). That Visa returns the value unchanged in the credential payload it signs for the merchant has not been shown by a run: until a sandbox response shows it, the form is not confirmed and nobody offers it. Visa's reference agent types the transaction reference as a UUID (`reference-agent-backend/src/schemas/commerce.py:72`), so that run may also find a 43-character base64url value refused.

1. Before payment the merchant shows the legal context as `card/visa-tap` rule 1 states it, and the agent checks it as that profile's rule 2 does.
2. On a match, when the agent asks Visa for the sale's payment credential, the `transactionReferenceId` of its `transactionData` entry, the per-sale reference the agent writes (`src/services/vdp_client.py:550`), is H's 32 bytes as unpadded base64url, 43 characters. lcp's `build` gives the value. The agent writes it into an API request, and Visa signs the credential payload that returns it: nothing the payer signs carries H, so the pairing's `carrier.signed` is null and its link is one Visa's signature, not the payer's, covers. H is not carried in `clientReferenceId`: Visa's reference agent sends there one fixed user id on every call (`src/utils/constants.py:17`; `src/services/vdp_client.py:454`, `:492`, `:542`, `:568`), so it names no sale.
3. `bound` takes `{"transactionReferenceId": …}`, the value as the merchant reads it from the credential payload Visa signs for the sale, and returns H. The payload's signature, and where in it the value sits, are the merchant's to verify and read; no run has shown them yet.
4. The merchant refuses a value whose H it did not issue for this checkout, or whose H it has seen used. The card authorization does not carry H.
5. **What a record proves**, as each pairing's `data.proves` states it; a record fills in the values set in angle brackets:
   - `card/visa-vic`: An account signed an agreement transaction carrying this ATR's hash on `<network>`, recorded in `<transaction>`, before this payment was taken or reported. This shows neither that the account is this payment's payer nor when this payment was taken, which nothing here reads. The agent's Visa Intelligent Commerce credential request carried this ATR's hash as its transactionReferenceId, which the seller read from the credential payload Visa signs for the sale. Verifying that payload is the seller's and was not done here, and nothing compares the agent or the cardholder with the account that signed the agreement. The card authorization itself does not carry the hash. This does not show that amount, payee or timing match the ATR's content.
