# x402

[x402](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md) is HTTP 402 payment: the
seller answers a request with a `PaymentRequired` document listing the options it accepts, and the buyer retries with a
payment for one of them. This package reads and writes x402 version 2 documents. Import the x402 pieces from
`@integraledger/lcp/x402`.

## The `legalContext` extension

Every x402 pairing advertises H in the same place: the document's `extensions.legalContext`, as x402's extension
mechanism defines it (an `info` object and a JSON Schema for it).

```json no-check
{
  "extensions": {
    "legalContext": {
      "info": {
        "type": "sha256",
        "value": "0xba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad",
        "legalContextUrl": "https://atr.seller.example/0xba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad"
      },
      "schema": { "$schema": "https://json-schema.org/draft/2020-12/schema", "type": "object" }
    }
  }
}
```

`LEGAL_CONTEXT` is the extension's key and `LEGAL_CONTEXT_SCHEMA` the full schema every pairing writes. The buyer
echoes `extensions` unchanged in its payment, as x402 requires. When the seller passes an agreement URL, `info` also
carries `legalContextAgreementUrl` ([the agreement URL](../concepts/buyer-gate.md#the-agreement-url)).

One document has one legal context. Each pairing that advertises into the same document with the same H, link and
agreement URL leaves `info` as it is and writes `LEGAL_CONTEXT_SCHEMA` as its schema; a different H, link or agreement
URL (one given and the other absent included) is refused as `x402/legal-context-conflict`. A challenge offering
options on several rails therefore carries one H, and the buyer's payment on any of them is bound to the same ATR.

## The request commitment

`requestCommitment({ method, target, body })` commits to the request the challenge answers: the method as received,
the request-target split at its first `?` into `path` and `query`, and `bodyDigest`, SHA-256 over the body bytes
exactly as received. The target is at most 8 KiB of visible ASCII starting with `/`, and the body at most 1 MiB.

`tie(accepts, request)` is the ATR's binding slot for every x402 pairing: `["x402", { accepts, request }]`, with every
option exactly as issued. `issuedDigest` is SHA-256 over the RFC 8785 form of one option or one commitment, for a
seller that keeps a digest of what it issued.

## Advertising several options

This example advertises one H into a challenge with two EVM options, one for EIP-3009 and one for Permit2, and shows
which pairing serves each option:

```ts
import { hash, isRefusal, pairingOf } from "@integraledger/lcp";
import {
  exactEip3009,
  exactPermit2,
  requestCommitment,
  type PaymentRequired,
  type PaymentRequirements,
} from "@integraledger/lcp/x402";

const base: PaymentRequirements = {
  scheme: "exact",
  network: "eip155:84532",
  amount: "10000",
  asset: "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
  payTo: "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
  maxTimeoutSeconds: 60,
  extra: { name: "USDC", version: "2" },
};
const viaPermit2: PaymentRequirements = { ...base, extra: { ...base.extra, assetTransferMethod: "permit2" } };
const doc: PaymentRequired = {
  x402Version: 2,
  resource: { url: "https://api.seller.example/v1/quote" },
  accepts: [base, viaPermit2],
};

const h = await hash(new TextEncoder().encode("the ATR's bytes"));
const link = `https://atr.seller.example/${h}`;

const first = exactEip3009.advertise(doc, h, link, base);
if (isRefusal(first)) throw new Error(first.code);
const both = exactPermit2.advertise(first, h, link, viaPermit2);
if (isRefusal(both)) throw new Error(both.code);

console.log(pairingOf(base), pairingOf(viaPermit2));
const read = exactPermit2.read(both);
console.log(isRefusal(read) ? read.code : `${read.offer.options.length} option, H ${read.h === h ? "matches" : "differs"}`);

const other = await hash(new TextEncoder().encode("another ATR"));
const clash = exactPermit2.advertise(first, other, link, viaPermit2);
console.log(isRefusal(clash) ? clash.code : "placed");

console.log(await requestCommitment({ method: "POST", target: "/v1/quote?tier=1", body: new TextEncoder().encode("{}") }));
```

```text
x402/exact/eip155/eip3009 x402/exact/eip155/permit2
1 option, H matches
x402/legal-context-conflict
{
  method: 'POST',
  path: '/v1/quote',
  query: 'tier=1',
  bodyDigest: '0x44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a'
}
```

## The x402 pairings

The x402 pairings, by scheme. The [pairings reference](../reference/pairings.md) states what each one proves, and
[Rails](./rails.md) gives the field on each chain and on Lightning.

| Scheme | Pairings | Where H rides |
|---|---|---|
| `exact` on EVM | `x402/exact/eip155/eip3009`, `x402/exact/eip155/permit2` | The signed authorization's nonce. |
| `exact` on EVM, ERC-7710 | `x402/exact/eip155/erc7710-salt`, `x402/exact/eip155/erc7710` | The salt of the redeemed leaf delegation, through MetaMask's DelegationManager; or, where the delegation signs no hash, the echoed extension only. |
| `upto` on EVM | `x402/upto/eip155/permit2` | The Permit2 nonce, for a signed maximum. |
| `auth-capture` on EVM | `x402/auth-capture/eip155/eip3009`, `x402/auth-capture/eip155/permit2` | The escrow payment's salt, or its salt nonce when the option binds a receiver authorizer or policy. |
| `batch-settlement` | `x402/batch-settlement/eip155`, `x402/batch-settlement/solana`, `x402/batch-settlement/cloudflare` | The channel's salt, the opening transaction's seller Memo instruction (`extra.memo`), or each request's echoed extension. See [Channels, sessions and subscriptions](./sessions.md). |
| `exact` on other rails | Solana, Stellar, XRPL, Hedera, Algorand, Aptos, Cardano, Casper, Concordium, NEAR, Polkadot Asset Hub, Starknet, Sui, Tron, TON, Lightning | Each rail's own field, or none (Aptos, Lightning invoice-named); see [Rails](./rails.md). |
| `upto` on Solana | `x402/upto/solana` | The Memo instruction of the transaction that opens a one-request payment channel. |

## Building on x402

`build(choice, h)` takes the document, the chosen option, the payer's account and the time in Unix seconds:

```ts no-check
interface X402Choice {
  required: PaymentRequired;
  accepted: PaymentRequirements;
  from: Hex;
  now: number;
}
```

It returns what the buyer's signer signs, in the rail's own form, and `complete`, which turns the signer's answer into
the x402 payment. On `x402/exact/eip155/eip3009` that is EIP-712 typed data; on the other EVM pairings a request whose
`kind` names the form (`"eip712"`, or `"erc7710"` for a delegation); on other rails a transaction or message to sign.

## Reading the payment

`bound(payment)` reads H from the payment; `reference(payment)` gives the keys to find its settlement;
`status(ref, reader)` reads the settlement through an `EvmReader` you supply, which answers four JSON-RPC calls:
`eth_getTransactionReceipt`, `eth_getBlockByNumber` for the `safe` and `finalized` marks, `eth_getTransactionByHash`,
and `eth_call` at a block number. A reader that throws `ReaderError`, or answers for another network, leaves the
payment pending, never failed. `pairingOfPayment(payment)` names the pairing that serves a presented EVM payment.

### A named transaction

The facilitator's settle answer, or the seller's own records, name the settlement transaction. `status` settles it
only when the transaction is this payment's. A transaction the reader does not hold is pending `not-found`, and a failed
read is pending `unreadable`; otherwise `status` answers with the reason, failed or pending as the paragraph after the
table says:

| Pairing | What the named transaction must hold |
|---|---|
| `x402/exact/eip155/eip3009` | The token's `AuthorizationUsed` log whose nonce is H, and the `Transfer` the same authorization produced, with payer, payee and value hashing to the reference's `transferLog` digest. EIP-3009's reference implementation and USDC emit the use and then its transfer, so the `Transfer` paired with the use is the first from its authorizer after it and before the token's next `AuthorizationUsed`, or, only when there is none, the last from its authorizer before it and after the previous one. Else `authorization-not-used` or `transfer-not-found`. |
| `x402/exact/eip155/permit2`, `x402/upto/eip155/permit2` | The `Transfer` the reference identifies; nonce H as 32 bytes anywhere in the transaction's input, where the call that spends the permit carries it, directly or inside a batch; and Permit2's record of nonce H for that transfer's payer: bit `H & 0xff` of `nonceBitmap(payer, H >> 8)`, set at the receipt's block and unset at the block before. Else `transfer-not-found` or `nonce-not-used`. |
| `x402/exact/eip155/erc7710-salt` | A `RedeemedDelegation` log from the DelegationManager for a leaf delegation, one whose delegate is the redeemer or the wildcard delegate, with salt H; and a `Transfer` from that leaf's root delegator, the reference's delegator. Else `binding-log-not-found` or `transfer-not-found`. |
| `x402/exact/eip155/erc7710` | No `status`: its keys identify any transfer from the delegator, and nothing in the transaction ties one to this payment, so a read of the chain alone never settles it. |
| `x402/auth-capture/eip155/eip3009` | The escrow's `PaymentAuthorized` log, or its `PaymentCharged` log where the option's `paymentFlow` is `authorization`, whose first indexed topic is the payment's identifier, and the token's `Transfer` from the payer to the escrow's EIP-3009 collector for the option's amount. Else `binding-log-not-found` or `transfer-not-found`. |
| `x402/auth-capture/eip155/permit2` | The escrow's log as for `x402/auth-capture/eip155/eip3009`; the Permit2 collector pays the operator's token store, which the payment does not name, so no `Transfer` is read. Else `binding-log-not-found`. |

On each pairing with a `status`, a transaction that reverted is failed `reverted`. A failed answer is given only once
the receipt's block is at or below the reader's `finalized` mark; above that mark, where the block can be replaced, or
where the mark cannot be read, the answer is pending with the same reason
([Reading settlement](./rails.md#reading-settlement)).

### Before a transaction is named

The pull pairings, where the payer signs an authorization that someone else executes later, also give what a
settlement reader needs while no transaction is named: `x402/exact/eip155/eip3009`, `x402/exact/eip155/permit2`,
`x402/upto/eip155/permit2`, `x402/auth-capture/eip155/eip3009` and `x402/auth-capture/eip155/permit2`.

- `authorizer(payment)` is the account whose signature authorises the pull, as lowercase hex.
- The reference's `authorization` names how the chain records the authorization's use: `scheme` (`eip3009` or
  `permit2`), `at` (the token, or the Permit2 deployment), `nonce`, `deadline` and `asset`.
- `authorizationUsed(ref, authorizer, block, reader)`, from `@integraledger/lcp/evm`, asks that contract whether the
  authorization had executed by a block. An EIP-3009 authorization executes only while the block's timestamp is below
  `deadline`, and a Permit2 permit only while it is at most `deadline`.

`x402/exact/eip155/erc7710-salt` gives `authorizer`, the delegator of the permission context's root delegation, and no
`authorization`: a delegation records no nonce and names no deadline.
